## Limits and accounting evidence

| Crossing budget | Enforced maximum |
|---|---|
| Public session | 4 per rolling minute; 10 per 30-minute lease; 1 in flight |
| Anonymous holder | 20 calls / $0.25 per UTC day; 2 active sessions; 30-day lease |
| Public Docent, project-wide | 100 calls / $1 per UTC day; 4 in flight |
| New anonymous holders | 100 per UTC day |
| Builder grant (future approved comparison) | 40 attempts / $10 total; 24-hour grant; 1 in flight |
| All jobs | $10 per UTC day |
| Provider | $20 per calendar month |

Transactions lock the runtime row first and quota buckets in stable order,
reserve the maximum verified billable amount, then commit **before** provider
I/O. Route changes, revocation and the master switch are rechecked at dispatch;
revocation/expiry also prevents a late result from being accepted. Duplicate UUIDs
cannot dispatch twice. Settlement writes exactly one Receipt and releases only
known unused reserve. A crashed/dispatched attempt becomes uncertain and retains
its full cost; expiry releases its concurrency slot, never blindly refunds spend.
Bound overruns record measured cost and disable the master.

Exact permanent call Receipt fields:
`id`, `time`, `job`, `model`, `agent`, `input_tokens`, `output_tokens`,
`cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, `cost_microusd`,
`cost_basis`, `validation_passed`, `result`.

`cost_basis` is measured / reserved / not-dispatched; micro-USD is integer
accounting, not a claim of reconciled provider billing. `accepted` means validated
proposal, never human publication. No prompt, question, answer, request hash of
visitor text, credential, headers, IP or identity details enter these Receipts.
Grant issue/revoke Receipts are separate and permanent.

The original nine-table design has these explicit implementation additions inside
its CREATE TABLE definitions: `routing_config.billing_contract`,
`call_leases.accounting`, `call_receipts.cost_microusd` and `cost_basis`.
They supply verified input/output price bounds, crash-safe snapshots and file 14's
cost evidence. Approved maxima and lease durations are constrained. No tenth
table, new DB role/extension, public RPC, trigger, cron or deployment automation.

## Two rollbacks and timestamp order

The forward name is Supabase's `YYYYMMDDHHMMSS_name.sql` format:
**`20261113120000_atlas_ai.sql`**. It is the only top-level forward migration;
future forward migrations must have later timestamps. Both rollback files retain
that same timestamp and live in a subdirectory outside the forward migration glob.
Silver must not recursively apply the rollback directory.

1. **Access-off after Receipts exist:**
   `20261113120000_atlas_ai.rollback.sql` disables master/routes, clears executable
   model IDs, revokes all leases and writes each revocation Receipt once. No table
   or Receipt is dropped; pending/uncertain costs remain. Tested twice for
   idempotency with both completed and in-flight calls.
2. **Full undo of failed unused first installation:**
   `20261113120000_atlas_ai.full-undo.sql` takes exclusive locks, requires zero
   **call AND grant Receipts**, no leases/call activity/nonzero accounting, and
   disabled null routes. It drops the nine tables in dependency order and then
   the new schema, without CASCADE. Any unexpected dependency aborts the entire
   transaction. If the original apply failed before commit and the schema is
   absent, it does nothing. Tests prove removal/reapply, refusal after one grant
   Receipt and atomic abort on an unexpected object.

Even issuing a metadata-only operator grant creates a permanent grant Receipt;
from that point onward use access-off. Silver removes the newly deployed function
with either rollback (preflight forbids overwriting an existing one). If Supabase
recorded the forward migration, full undo also requires approved reconciliation
of that one history entry using the supported tool; the SQL never edits
Supabase's internal migration history. Record the rollback in `lane/ops/`.

